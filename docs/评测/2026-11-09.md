# 2026-11-09：维护者自测与 RC2 离线修复

## 反馈与范围

维护者在 WSL2 安装并试用 RC1 后，口头反馈提供的示例“都没什么问题”，但错误较多的代码很快进入创意模式，离线创意只是回显输入。没有收集完整终端记录，不将这条反馈量化为全部平台/意图验收，也不算独立受邀测试。

本地额外 `hello.c` 的实际报告为 creative_fallback / print_input：缺少 include 的 `#`，使用智能引号、缺少标点、括号不配对，且含 C++ `cout <<`。原文件和旧报告保持不动。该混合输入不能仅靠 C 语法修补承诺转换；C++ 特征只作提示。

用户选择本轮优先多错误 C 修复和离线降级说明；规则与报告契约见 [ADR-0018](../adr/0018-bounded-rule-refinement-and-degradation.md)。版本为 `0.1.0rc2`，仍是本地候选，没有发布。全程无真实模型请求，不读取维护者真实密钥。

## 同输入 RC1 / RC2 对照

新增 8 个受控多错误 C 场景，先给定行为预期，再分别交本机已安装的 RC1 wheel 与 RC2 源码路径执行；都使用 offline。RC1 wheel 对应代码 `595e35b`，此前安装时已与 Linux CI 的 SHA-256 核对。显式使用用户工具目录的命令，避免 `uv run` 的 PATH 选择项目环境而误测两份相同版本。

| 场景 | RC1 行为通过 | RC2 行为通过 |
| --- | --- | --- |
| 多个缺失分号 | 否 | 是 |
| 缺 # + 拼写 + 全角 + 分号 | 否 | 是 |
| 智能引号 + 缺括号/分号 | 否 | 是 |
| Unicode 字符串前后补分号 | 否 | 是 |
| 循环内语句 + 其他分号 | 否 | 是 |
| 条件分支（正/负输入均检查） | 否 | 是 |
| 注释/字符串保护 + 其他错误 | 否 | 是 |
| 缺右花括号 + 其他错误 | 否 | 是 |

8 个场景共 9 组行为输入，RC1 **0/8**、RC2 **8/8**。判据包括 repaired 状态、完整输出和退出码，不能把 RC1 的兜底退出 0 算修复成功。原始源码/预期/实际/状态/次数见 `data/rc2-multi-error-comparison.json.gz`，测试定义见 `tests/e2e/test_multi_error.py`。这是一批针对性合成回归，不是用户真实项目成功率；不加入 M4 原有分母。

## 首轮 Windows 失败与 CRLF 修补

初版代码 `3dc28c7` 的 [CI 42588343839](https://github.com/wuqiuwangtian/yescc/actions/runs/42588343839) 失败：两个 Windows e2e job 各有 4 个新增多错误场景失败，Windows package smoke 的 multi_error 也失败；Linux 与非 e2e 检查通过。没有跳过或修改其行为 oracle 来取得通过。

两个原因分别复现：缺 # 的行尾规则没有接受 CRLF；原始输入保留 CRLF，但 Windows `write_text` 默认翻译换行，临时候选变成额外空行，GCC 给出的修复行号不再对应内存文本。修补后内部临时候选、落盘修复源码与 patch 都显式保持传入换行。

新增 LF/CRLF 两组完整多错误用例和可在 Linux 复现 Windows 写入转换的测试；定向 35 passed，全量 **550 passed / 1 Windows-only skip**（86.21 s），ruff/mypy/Windows 平台 mypy 通过；干净安装 12/12 及离线基准 130/130、70 未评测也重新执行。新原始记录为 `data/rc2-crlf-package-smoke.json.gz`、`data/rc2-crlf-offline.json.gz`，不覆盖上一版 RC2 的本地记录。Windows 的最终结论仍需修补提交的新 CI，不能用模拟代替。
