# 2026-11-12 创意兜底专项：真实模型、作品质量与改进建议

结论：当前创意兜底能产生贴题的小作品，但输出质量尚不稳定，不宜仅凭“可运行率100%”作为项目特色已经成熟的依据。最先处理工具链承接、模型兼容和输出完整性，再采用更明确的创意提示；候选额度分配是需要维护者决定的另一项取舍。本轮只测试与提出建议，没有修改产品行为、合并或发布。

## 1. 测试对象与口径

- 被测提交 `1a9f139`，源码指纹 `5ebf765f60a439dc62d734357e82d0a98262af2ab30a105fe6180cce4fb7adf6`；Python 3.11.15、Linux/WSL、本机真实GCC。普通源码环境，未重新测试Windows或冻结包的真实模型质量；用户安装仍为RC4。
- 请求沿用本机配置 `deepseek-chat`，所有真实响应的model字段为 `deepseek-flash`。服务端别名/权重可能变化，不能把同请求名视为与历史M5完全相同的模型。
- 主集50个不同输入：原M4的30个fun输入原字节复用，另由不继承开发历史的AI设计20个，覆盖情绪、隐喻、混合语言、emoji、转义、多行、伪指令、坏C、空白和零字节。主集用公开 `--play --json --no-cache`，真实编译后单独实际运行。
- 另外选5个输入各追加2次冷生成（共10次，不挑最好的一次替代结果）；10个预选输入做实验提示对照；3个模型名/思考模式探测；6条实际 `run` 路径。合计79个任务、80次真实Chat Completions请求（另1次只读模型列表查询不计模型生成次数），没有重跑完整200例收费基准。
- 两位不继承开发历史的AI按冻结量表独立评审70份作品（主集50+追加重复10+实验提示10）。匿名材料只给输入、来源、实际输出/执行摘要及源码，不给实验条件；评审者未读取产品源码或彼此报告。主导者另核对原始字节、源码、请求数、评分ID和阈值。
- 量表四维各0–3：相关性、创意、程序性、完整性。`strong`为总分≥9、相关性/完整性均≥2、创意/程序性均≥1，且非原文打印/固定梗；它只是本专项“较好作品”的预设综合标准，不是人工评分或正式发布门槛。贴题诗歌/ASCII作品不因没有复杂算法被判零。
- 所有主集输入和评分标准在主集调用前冻结。补充数据SHA `45bd4c2ac60ff4ce36c758817a08ecb8eb2c9d7bd35b48a3713ee1594d76daf5`；量表SHA `42c163715b9205d20033cadfcdd4a9dc16a2de83ab5ab76112d78cc04a84fa41`。M4原固定200例及指纹没有修改。

44个模型作品的创意维度平均分，两位均为 **1.30/3**；创意≥2的作品分别16/44、18/44。这更接近当前短板：能正常生成，不代表输出足够有特色。两位评审全部70项有7项标签分歧，原分数与理由完整保留。

### 确实有较好作品

**“我的显卡想退休”**：默认产物把GTX风扇想去海边、RTX从光追改追落日、RX从挖矿改挖花盆连成退休事务所，两位均认可。实际输出片段：

```text
GTX 660: 风扇转了十年，申请去海边吹风。
RTX 2080: 光追追累了，想追落日。
RX 580: 挖矿退役后，只想挖挖花盆。
退休金：0 瓦，风扇转速：0 RPM。
```

**“今天什么都没做成，好想变成一块不需要证明自己的石头。”**：输出石头图形并写“石头不需要证明自己。它只是在那里，就已经完成了。”，回应了原输入情绪；不是只有计数循环才算作品。

### 能跑但不完整或缺乏创意

- **非法UTF-8，F10“赛博土豆”**：把二进制数组算出的178用`%c`输出为单字节`0xB2`，stdout不能按UTF-8解码。源码、原始字节及哈希已保留，不能把宿主显示的`�`误当字体缺字。两位都把完整性评为1。
- **正文缺行，F18“三个笑脸”**：先`puts`确定stdout为窄流，随后`wprintf`的三条表情名称没有输出。实际只剩标题和结尾，退出仍为0、字节仍是合法UTF-8。说明“非空+合法编码”也不能保证作品完整。
- **模板化**：不少作品把输入翻译成英文，随后统计字节/字符或加通用状态行。S14锅里会议的默认作品基本是“土豆要求加薪、胡萝卜反对加班、盐宣布休会”的提纲改写，两位对其是否达到strong存在分歧，创意维度都只有1。
- **重复不稳定**：5输入各3次，15个模型作品都能运行；追加10次中两位分别认可4个、5个strong。显卡同题另一次只输出“retirement request acknowledged / render with kindness”，明显不及前述退休剧场。没有按最好一次汇报。

## 3. 失败根因与实际入口

### 3.1 三次失败主要是链接，不是想不出作品

F02“奇变偶不变”、F22“纸飞机与宇宙”、F28“风扇摇篮曲”各两份模型候选，都用了`sin/cos/floor`等数学函数。产品GCC命令没有`-lm`，模型收到失败诊断后仍继续使用它们，最终退回原文打印。

独立agent提取6份真实候选，保持源码字节不变，用同一GCC分别不带/带`-lm`编译：**6/6前者链接失败，6/6后者编译并运行成功**，分别输出三角函数表、纸飞机轨迹和风扇波形。该实验不追认默认产品成功，也不等于六份作品创意都好。源码审查由AI完成，原字段`manual_source_review`不能理解成人工验收。

### 3.2 配置名和默认思考不是透明替换

原配置别名探测成功，实际响应为deepseek-flash；直接请求deepseek-flash的同类输入则`finish_reason=length`，1024个输出token全部为reasoning，content为空，产品只报告“模型输出中没有JSON对象”并打印原文。另一次仅在实验请求禁用thinking，即生成并运行成功。

这三个都是独立探测，不混入主集；只足以证明接入差异值得处理，不能估计所有新模型调用的失败率。供应商当前[思考模式文档](https://api-docs.deepseek.com/guides/thinking_mode/)说明默认开启及显式开关；产品尚无相应供应商能力设置，不能直接更换名称后宣称升级完成。

### 3.3 修复与创意共用额度

六条真实CLI `run` 路径结果：

| 输入/方式 | 实际结果 | 模型请求 |
| --- | --- | ---: |
| 普通未知文本“石头竞选星期八市长” | model_creative，竞选公告/票数/日历外当选 | 1 |
| 明确`--play`的影子/路灯隐喻 | model_creative，英文短诗 | 1 |
| 坏C默认模式 | 两次补丁均被拒绝，额度耗尽后print_input | 2 |
| 同一坏C直接`--play` | model_creative，外星猫/宇宙/星期八的小程序 | 1 |
| 正常中文任务“十只鸭子庆祝” | generated，不冒称creative_fallback | 1 |
| 合法C | native_ok，输出native preserved | 0 |

坏C是`int main(void) { return 外星猫(宇宙[0], 星期八); }`。默认路径的两次补丁删除整段原文，按现有规则拒绝后已无模型候选额度给创意。这里必须保留修复/创意的实际分配含义，不能仅因最终creative_fallback就说模型创作发生了。

## 4. 提示词改善的受控小试

没有修改`src/`。实验驱动仅在创意消息末尾增加：遵循输入语言、选择一个完整构思（小模拟/图形/叙事/诗歌）、避免把字节统计/翻译/复述当主体、保全UTF-8、保持短小且无额外输入。提示在预算计算之前加入；模型、采样温度0.4、输出1024 token上限、工具链和两次候选限制保持相同，没有同时禁用thinking。

10个匹配输入在查看主集产物前按风险预选，非随机抽样；两条件各一次，未随机交错，模型有随机性及时间漂移。它是建议方向的试验，不能作统计显著性或整体升级保证。

| 同10个输入 | 默认 | 实验提示 |
| --- | ---: | ---: |
| 模型程序正常执行 | 9/10 | 10/10 |
| 模型程序且输出合法UTF-8 | 8/10 | 10/10 |
| strong，评审A | 4/10 | 10/10 |
| strong，评审B | 5/10 | 9/10 |

上表strong分母都是10个输入，print_input只记未产出strong，不给它编造模型质量零分；四维均分另按实际模型作品计算，原记录中明确分母。

## 5. 建议顺序与验收方式

以下是建议，尚未实施或获正式发布验收：

| 优先级 | 建议 | 为什么/如何验收 |
| --- | --- | --- |
| P0 | 明确AI生成C的工具链能力，支持必要libm或让生成器准确知道链接限制 | 先重放6份原始候选，再双平台验证；只作用于AI候选的方案需明确记录实际命令，不给合法原生程序暗加参数 |
| P0 | 来源与有效作品分开计分；处理finish_reason、空content和截断 | print_input/easter_egg不得进入模型成功率；JSON失败不能按一次候选+最终退出0计首候选；兼容性探测应能明确解释thinking/length，不静默装作创意成功 |
| P0 | 在评测与显式run路径核对输出质量底线 | 至少检查非空、UTF-8、超时/超量、退出码，并加入宽窄流/完整性回归；不能为验证而让默认build偷偷执行AI代码，也不能声称机械检查可证明贴题 |
| P1 | 采用本次“明确构思、语言匹配、UTF-8、避免通用统计”提示方向 | 将它作为独立提示版本，完整50例+同一重复集冷评测，保留失败和独立评分；同时回归生成/修复，不能只看预选10例 |
| P1 | 保持短程序、完整小作品；同时限制JSON/源码输出规模 | 120行允许量与1024token输出上限不协调，先鼓励约15–45行与紧凑JSON；供应商结构化输出需验证支持，不能仅加“多写一点”导致截断/费用增加 |
| P1，需决策 | 修复与创意的候选额度分配 | 用户要“挽救代码”还是“转创作”是取舍；可保留显式play作明确入口，或在现有总上限内预留创意候选，代价是少一次修复机会；不擅自加次数/加钱 |
| P2 | 作品题材更丰富，建立持续质量集 | 覆盖小模拟、图形、节奏、叙事、诗歌；不用强迫所有题材循环/动画，也不把固定模板库当创作质量。与原文回显的最低功能分开统计 |

我的推荐：先做前三项可用性/证据修补，再落地提示方向并按相同基线复测；不要先换更贵模型或单纯调高temperature。当前证据表明，已有模型能力被提示、链接参数和额度分配明显限制。
