# “包容你的编译器”初版需求报告

版本：v0.4｜日期：2026-11-04｜状态：已确认 YesCC 命名、C 优先的 AI 范围、创意兜底语义与 MIT/PyPI 发布形态；M1 已实现，未发布。

## 1. 产品定位与原始要求

这是一个娱乐型 AI“编译器”，面向被报错折磨的程序员，以及对写代码感兴趣的小白。用户可以写标准代码、带语法问题的代码，甚至完全使用自然语言；工具尽量理解意图，替用户完成修复、转换和编译。

原始要求完整保留如下：

- 不向用户抛出传统编译器式的错误和警告，形成“无论你写什么，它都包容你”的体验。
- 最基本目标是兼容所有编程语言。正常、符合要求的代码，其运行结果应与正常工具链完全一致。
- 对缺少括号、中文输入法标点等问题，尽可能理解意图后编译；不保证推断一定正确。
- 极端情况下可直接输入自然语言，生成可运行代码。
- 至少在 Linux 与 Windows 上，以类似 gcc 的方式使用。
- 理想形态包含 VS Code 等编辑器插件。
- 关键挑战：理解真实意图，以及编译速度、调用成本与结果质量的取舍。

## 2. 产品承诺中需要先明确的边界

### 2.1 “所有语言”保留为目标，但不能直接成为有限版本的完成声明

建议采用可扩展的语言适配器，逐步接入已有编译器、解释器和构建工具。每个语言及版本分别声明“原生通过、语法修复、自然语言生成、项目构建”四类能力，不能因为模型认识某种语言就称之为完整兼容。

本报告建议先对少数语言做出可靠实现；该分期已于 v0.3 确认（见 §11.1），v0.4 进一步把 AI 修复与自然语言生成收敛到 C（见 §11.2）。在原始“所有语言”的字面要求下，任何只支持部分语言的首版都尚未满足该项要求。未覆盖语言应给出平和的状态说明，不能假装已编译成功。

### 2.2 “不会报错”与“必定成功”需要分开定义

建议将体验承诺定义为：默认不把内部诊断和堆栈直接甩给用户，系统先尝试修复；无法完成时，用简短、友好的状态说明结束，并保留可查询报告。

任意文本可能没有唯一意图，依赖或工具链也可能缺失，因此不能保证任意输入都得到正确程序。若坚持“任何情况都必须输出成功且得到正确程序”，则当前需求没有可信的通用实现与验收方法。该边界已于 v0.4 调整为：输入类失败默认进入创意兜底，但兜底结果必须单独标注（见 §11.2 与 [ADR-0009](adr/0009-product-promise-and-status-machine.md)），不能用它冒充原程序被修复。

## 3. 关键用户场景

| 场景 | 输入示例 | 期望行为 |
| --- | --- | --- |
| 标准程序 | 合法 C、Python 等源码 | 使用对应原工具链，不让 AI 重写 |
| 少量语法错误 | 缺半个括号、全角分号 | 尽量以小改动修复，真实验证后产出 |
| 局部混合表达 | 函数中写“这里把列表按价格排序” | 结合上下文生成局部实现，不改无关部分 |
| 完全自然语言 | “读入一串整数，输出最大值” | 确定输入输出约定，生成指定语言代码并验证 |
| 多解或描述不足 | “排个序”“处理一下这个文件” | 采用可查询的保守假设；关键差异无法判断时允许一次简短澄清 |
| 无法修复 | 缺少必要文件或外部服务 | 有限尝试后结束，说明缺少什么，保留报告 |

对新手，默认不展示复杂技术细节；对程序员，提供原始诊断、修改差异、生成代码、假设和验证记录的入口。娱乐感可以体现在提示语，但不能嘲讽用户或伪造成功结果。

## 4. 命令行体验（草案，尚无可执行程序）

以下 `yescc` 为临时命令名，仅用于描述交互。

```text
yescc hello.c -o hello
yescc run script.py -- arg1 arg2
yescc idea.txt --lang python --run
yescc hello.c --explain
yescc hello.c --strict
```

- 编译型语言默认产出工具链支持的目标文件或可执行文件；类似 gcc 的编译命令不自动运行程序。
- 解释型语言必须说明产物与运行方式；统一入口不意味着所有语言都转换成机器码。
- `run` 或 `--run` 才触发用户程序执行。用户程序参数与编译工具参数使用明确分隔，避免错传。
- `--lang` 用于消除语言猜测歧义；v0.4 起自然语言生成的默认目标语言为 C（可配置并写入报告）。
- `--explain` 查询已经发生的修改、假设和验证结果；不要为查看报告再次付费调用模型。
- `--strict` 为建议的原工具链模式：跳过 AI 修复，允许查看原诊断，供调试与集成使用。它是用户主动选择的次级模式，默认体验仍面向无报错目标。

建议将程序输出完整保留在 stdout/stderr，不让产品提示混入 stdout。编译状态可以在交互终端简短显示，非交互场景使用结构化报告与退出码。未成功生成产物时不能返回成功；显式运行时应正确反映程序退出状态。取消和超时应可被脚本识别。

源文件默认不覆盖；修复后的代码、差异、工具链信息和报告保存为单独产物，允许用户选择应用修改。构建失败不能留下看起来属于本次成功构建的陈旧可执行文件。

## 5. “合法代码保持一致”的验收定义

正常输入优先走原生路径，是满足一致性目标的核心设计建议。GCC 本身包含预处理、编译、汇编和链接等环节，因此兼容不能只检查语法是否通过。[GCC 官方调用说明](https://gcc.gnu.org/onlinedocs/gcc/Invoking-GCC.html)

建议将一致性范围定义为：**同一语言实现、版本、操作系统、目标架构、编译参数、依赖、输入、工作目录及相关环境下，原工具链成功接受的程序，包装工具保持其构建与运行语义**。

具体要求：

1. 原工具链成功时，源码不被 AI 或标点规则改写，不因警告而自动改语义。
2. 保留宏、包含路径、链接顺序、优化级别、语言标准、环境和编码等约定；无法支持的参数应明确列入兼容矩阵。
3. 不暗中把 C 换成 C++、把某个版本换成另一个版本，或把所有语言翻译为 Python 后宣称原生一致。
4. 不把临时文件位置变化造成的导入路径、`__FILE__`、资源路径变化当成可忽略问题。
5. 对确定性测试比较 stdout、stderr、退出码以及约定的文件结果；浮点与非确定性行为按任务定义比较方法。
6. “完全一致”不解释为跨平台二进制逐字节相同。不同工具链、未定义行为、外部状态和非确定性程序不能据此得到通用的输出一致保证；这些情况应单独记录范围与限制。

建议有编译警告但构建成功时仍使用原产物，默认将诊断收进报告。`-Werror` 等显式参数不能被偷偷删去来制造成功；参数引起的失败需在兼容模式和容错模式中明确定义。GCC 官方文档也区分了阻止编译的错误与通常不阻止编译的警告。[GCC 诊断说明](https://gcc.gnu.org/onlinedocs/gcc/Warnings-and-Errors.html)

用户程序自己打印的错误文本或运行时失败不属于编译器诊断；若默认吞掉这些输出，会与合法代码行为一致的要求冲突。建议原样保留程序行为，运行时自动修复作为未来独立能力，不默认启用。

## 6. 处理流程（建议）

```text
读取输入、参数与语言提示
    ↓
源码输入：先运行原工具链；成功则直接产出并结束
    ↓ 未成功
区分语法/类型问题、缺依赖、路径和环境问题
    ↓
尝试可验证的小范围规则修复
    ↓ 仍未成功
向 AI 提供必要源码、诊断与上下文 → 生成补丁
    ↓
在隔离环境中重新构建，执行已有测试或指定样例
    ↓
预算内有限迭代 → 产出结果或友好终止，保存报告

自然语言输入：语言与输入输出约定 → 生成代码 → 同一构建/验证流程
```

区分问题类型十分重要：链接库不存在、工具链未安装或认证失效时，模型不应通过删除功能、替换为常量输出或伪造依赖来“修好”。工具可指出所缺条件，但不默认修改全局环境或自动安装未知依赖。

### 6.1 规则修复

优先考虑全角标点、局部缺失符号等小范围问题，但只能在识别词法结构后尝试。中文字符串、注释和合法 Unicode 标识符不能被全局替换；少一个括号也可能有多种合法补法。

每个补丁都重新交给真实工具链验证。若有多个通过候选，可比较改动范围、现有测试和上下文；“改动最少”只是启发式，不是意图正确的证明。

### 6.2 AI 修复与意图理解

优先依据：用户明确描述与样例、现有测试、类型和接口约束、相邻代码和注释，最后才是惯例假设。若测试本身可能有问题，应将冲突写入报告，不能删改测试来通过验证。

模型只获取任务必要上下文；先定位问题再扩展相关定义，避免每次发送整个项目。单文件先支持，再验证跨文件与构建系统。修复或生成后必须真正编译；有样例或测试时继续验证，但要区分“可构建”“测试通过”和“已证实符合意图”。

程序修复研究支持利用诊断反馈定位与生成候选，但并不能保证任意输入的真实意图可恢复。[DrRepair 论文](https://arxiv.org/abs/2005.10636)

## 7. 语言与平台兼容范围（建议矩阵）

| 能力 | 首批范围（v0.3 已确认） | 后续扩展 | 当前状态 |
| --- | --- | --- | --- |
| 原生工具链通过 | Python、C、JavaScript | C++、Java、Go、Rust 等及相应版本 | M1 已实现三语言单文件，双平台 CI 验证；AI 修复/生成仅 C |
| 少量语法修复 | C 单文件程序（v0.4 起 AI 仅 C） | Python/JS 修复、类型与跨文件修复 | 未实现 |
| 自然语言生成 | 明确输入输出的 C 短程序 | Python/JS 生成、多文件应用与外部服务 | 未验证 |
| Linux 使用 | 明确一个发行版与工具链组合 | 扩大发行版/架构矩阵 | 基线：Arch/WSL2 开发 + Ubuntu CI，已验证 |
| Windows 使用 | 原生 PowerShell/CMD 下可调用 | 更多工具链与终端组合 | M1 已在 windows-latest 原生验证；MSVC 未支持 |
| 编辑器 | 暂以后续 VS Code 插件为目标 | 其他支持语言服务的编辑器 | 未开发 |

C 在 Windows 上要明确使用 MinGW-w64/GCC、Clang 或 MSVC 中哪一组，不能把它们的参数视为完全等价。编译器、解释器和模型的安装/发现方式属于产品要求，不能要求小白自行猜测缺什么。

这里列出的语言顺序只用于建议验证顺序，不是已经确认的删减或支持声明。

## 8. 速度、成本与本地模型

所有数值均为待基准测试修订的建议门槛。

| 路径 | 建议指标 |
| --- | --- |
| 原工具链成功 | 云端 token 为 0；已启动命令的包装额外开销 P95 ≤ 200 ms，工具链耗时另计 |
| 规则可修复 | 额外处理与验证开销 P95 ≤ 1 s，小型单文件基准，工具链本身耗时单列 |
| 单轮 AI 修复 | 参考设备/网络下，100 行以内程序从提交到产物 P95 ≤ 10 s，统计命中与未命中缓存 |
| 失败收敛 | 建议最多 2 轮模型调用，同时设置 token、费用和总墙钟时间上限，任一触顶即停止 |
| 交互终止 | 支持取消，停止后清理本次任务，不再继续发起模型调用 |
| 本地模型 | 分别测冷加载、热推理、内存、吞吐和修复正确率，不预设一定优于云端 |

缓存键至少覆盖源码与相关依赖摘要、工具链版本、平台、参数、模型和修复策略版本；不能仅按错误文本复用。禁止直接复用不同用户的私有代码或补丁。

云端成本按输入/输出 token、调用轮数及实际价格计算；每任务费用和每个正确结果的费用都应记录。候选数量、重试次数和上下文扩展必须受预算控制，不能靠无限生成换“零报错”。

建议优先级是原工具链 → 可检查规则 → 本地代码模型 → 可选云端升级。若本地模型不够好，可以只承担定位、分类等小任务；具体分工以对照实验为准。云端上传范围与开关应清晰可控，不默认将整个仓库发送给模型。

## 9. 验证执行与产物要求

AI 生成或修复的代码在验证阶段可能读写文件、运行子进程或访问网络。建议验证默认使用隔离目录、资源限额和受控权限，限制网络，显式传入所需输入，避免把测试变成对用户真实环境的执行。

Linux 与 Windows 的隔离实现需要分别验证；某平台隔离尚未就绪时，不可宣称已提供同等保障。编译/验证与用户主动选择的本地运行要区分，受限环境也不能被用来证明所有环境中的行为一致。

每次尝试建议生成报告，至少包含：输入摘要、语言及工具链版本、原始诊断、实际补丁、生成代码、采用的假设、构建状态、测试范围、已知未验证项、耗时、token/费用和退出状态。报告默认本地保存，日志中不记录密钥等无关数据。

## 10. 验收方案与成功标准

| 样本类别 | 主要判定 | 建议门槛 |
| --- | --- | --- |
| 已知正确的原生程序 | 同环境对照原工具链，比较行为 | 发布回归样本 100% 通过，合法输入源码 0 修改、0 模型调用 |
| 受控语法损坏 | 与损坏前程序的独立行为测试比较 | 首批单文件常见错误意图正确率 ≥ 90%，仅作为初步建议 |
| 真实错误程序 | 不只编译通过，还看独立测试与人工核对 | 各错误类型单独报告，不把合成样本结果外推 |
| 自然语言任务 | 预先定义的隐藏测试、边界输入及必要人工判断 | 报告 pass@1；先测基线，再固定首版门槛 |
| 不可处理任务 | 有限终止、友好状态、无伪造成功 | 退出码和报告状态准确，未成功不留下冒充成功的产物 |
| 跨平台 | 同一测试集在原生 Linux/Windows 运行 | 分别记录版本与结果，路径/编码/参数行为覆盖 |

核心指标为**意图正确率**，构建成功率是必要但不充分的指标。模型自己生成的测试可作补充，但不能成为唯一验收依据。测试设计与对照组合见[技术参考与验证计划](技术参考与验证计划.md)。

必须单独覆盖：合法但会警告的代码、`-Werror`、中文字符串与注释、不同换行和编码、含空格路径、标准输入、链接/导入依赖、无穷循环、程序自身的 stderr 与非零退出码。

## 11. 分期建议与待决策事项

1. **可行性阶段**：建立三类样本与严格基线，验证原生路径一致性、常见错误修复、自然语言短程序正确率和预算收敛。
2. **首版建议**：Linux/Windows 命令行、首批语言的明确版本矩阵、单文件容错、自然语言生成、报告与源文件保护。
3. **后续迭代**：跨文件、更多工具链和语言、更高质量本地模型，再提供复用同一核心的 VS Code 插件。先用命令/任务和报告界面即可；确需诊断与代码操作时再接语言服务器。[VS Code 任务扩展文档](https://code.visualstudio.com/api/extension-guides/task-provider)

原待决事项的处理（v0.3）：分期语言支持、“不会报错”采用友好终止定义、默认自然语言目标语言（Python）、可用云端与预算上限已确认；首批工具链最低设备基线与“歧义较大时允许一次澄清”仍待实测后决定。

我的建议是：娱乐体验要始终“先帮用户解决”，但原生行为、真实执行与可追溯修改是信任基础。首个值得证明的亮点，是合法代码不受干扰、常见小错误能在低成本下得到正确修复，然后逐步扩大输入自由度。

## 12. GitHub 同类项目与复用补充

已补充[开源项目调研](GitHub开源项目调研.md)，重点核查 agenticc、Aider、Natural、DrRepair 与 Judge0。agenticc 在娱乐定位与混合语言输入上很接近，但核查到的产物通过模型返回输出，不能直接替代原程序真实执行，也不满足本报告的原生一致性要求。

建议可行性阶段先比较现成组件的集成成本：考察 Aider 的补丁与有限修复循环，参考 Natural 的生成/CLI/编辑器分层，参考 DrRepair 的诊断样本与评测；服务化验证可进一步评估 Judge0。本项目重点保留原生直通、极简体验、语言适配、真实验证与预算控制，减少重复建设外围能力。

上述均为待验证的复用建议，许可证和维护快照见调研文件。本次未安装、执行或复制第三方代码，尚未选定依赖；所有语言与 Linux/Windows 的原始目标继续保留。
