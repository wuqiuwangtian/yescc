# 使用、隐私与 Windows 安装

适用于当前源码；已发布 alpha 的能力与后续修补分开，版本状态见[路线图 §10](项目路线图与发布计划.md#10-待决事项与下一步)。能力矩阵与运行限制以 [README](../README.md) 为准。

## Windows 原生安装与验收

需要 Windows 原生 Python ≥3.11、uv、Git；C 构建另需 GCC，JavaScript 直通另需 Node.js。MSVC 不支持。WSL 的运行结果不算 Windows 原生验证。

可使用 MSYS2 的 UCRT64 GCC。安装和更新步骤以 [MSYS2 官方安装指南](https://www.msys2.org/)为准；UCRT64 的选择依据见[官方环境说明](https://www.msys2.org/docs/environments/)。在 **MSYS2 UCRT64** 终端安装：

```bash
pacman -S --needed mingw-w64-ucrt-x86_64-gcc
```

在 PowerShell 中临时配置工具链路径，再运行源码（路径按自己的安装位置调整）：

```powershell
$env:Path = "C:\msys64\ucrt64\bin;" + $env:Path
Get-Command python, uv, gcc
python --version
gcc --version
git clone https://github.com/wuqiuwangtian/yescc.git
Set-Location yescc
uv sync --extra dev --locked
uv run yescc --version
Set-Content -Encoding ascii hello.c '#include <stdio.h>
int main(void) { puts("hello"); return 0; }'
uv run yescc run hello.c --offline
uv run pytest tests/e2e/test_platform_boundaries.py -q
```

预期合法 C 原样构建运行；平台测试中的 POSIX 信号用例会跳过。`Get-Command gcc` 应指向预期工具链；若缺 DLL，保留同目录在 PATH。部分 MinGW 链接器对绝对 Unicode 输出路径会失败，可在项目目录使用相对 `-o output.exe`；YesCC 保留原生失败，不声称修好了工具链。UTF-8（含 BOM）与 CRLF 受支持，其他编码返回 101。

本指南命令未在维护者的实体 Windows 上手动走完；自动化原生 Windows 结果见评测记录。不要把 CI 的 PATH 配置推定为用户已经安装好工具链。

## 数据流与清理

| 场景 | 发送给模型的数据 | 本地留下的数据 |
| --- | --- | --- |
| 原生成功、`--strict` 或 `--offline` | 无 | 构建产物、报告；可能有原生诊断 |
| C 模型修复 | 当前源码、文件名、编译诊断、前次失败反馈 | 候选源码、实际 patch、原始 diff、调整记录、模型统计 |
| 自然语言/创意生成 | 输入文本、生成要求、前次构建反馈 | 生成源码、报告、候选缓存 |

云端端点首次提示上传；`--offline` 才是明确禁止模型请求的开关。自定义端点由你配置，服务端的数据保留政策需另行确认。回环地址被当作本地端点，这不证明它没有代理到云端。基准参考程序与预设答案不进入模型提示词。

`.yescc/<stem>/` 内的报告、源码、patch 和 `--trace` 日志可能包含敏感源码、文件路径和编译器回显；不要直接附到公开 issue。模型缓存位于平台用户缓存目录的 `yescc/model-v1`（可由 `YESCC_CACHE_DIR` 指定），保存模型响应。`--no-cache` 跳过缓存读写，不会清除旧缓存；停用命令后按需删除上述目录。文件没有加密，依赖操作系统权限，不能抵御同用户的其他进程。

API key 从环境读取，用作授权请求，不主动写入模型提示词；HTTP 错误回显中出现的当前 key 会先替换为 `[REDACTED]` 再截断。该处理不是任意秘密扫描器，不能保证移除你写在源码中的凭据。源码或模型响应中的秘密仍可能进入日志/缓存，提交前必须自行检查。

AI 运行仅尽力隔离：临时 cwd、环境白名单、超时、进程树清理；绝对路径和符号链接仍能访问宿主文件，输出没有产品级限流。需要处理不可信代码时，应另选容器或虚拟机环境。

## FAQ

**为什么编译成功仍不能称为修复正确？** GCC 检查语法和链接；程序可能算错、读取错误输入或改变原意。报告 `repaired/generated` 表示候选通过构建，需另用行为测试确认。

**为什么提示“生成成功”但退出不是 0？** 构建状态和运行结果分开。查看 `result.program_exit`、`limits` 和运行输出；超时为 124，用户取消为 130。创意兜底始终标为 `creative_fallback`。

**预算 0.05 是人民币吗？** 不是，是 USD。云端缺单价时不请求；`cost_known=false` 时 `cost_usd` 是已知小计。失败请求可能收费，预算是按配置价格估算，不能代替供应商账单。

**模型补丁行号不对怎么办？** 可按唯一精确旧文本块定位并重算行数；空白或正文不符、重复上下文、重叠和整文件改写仍拒绝。原始响应和调整说明进入报告，规则见 [ADR-0017](adr/0017-exact-context-patch-normalization.md)。

**Python/JS 错误也会修吗？** 当前 AI 目标只有 C；Python/JS 保留原生直通。需要原生失败原样返回时使用 `--strict`，避免进入创意兜底。


## RC 本地安装与反馈

当前 RC 尚未发布到 PyPI/TestPyPI；不要把 alpha 安装命令当成 RC 安装。先在已检出的开发分支运行 `uv build`，然后在新的虚拟环境用 `uv pip install --python <新环境的 python> dist/yescc-0.1.0-py3-none-any.whl` 安装。只有维护者按锁文件约束执行的评测对应本仓库保存的依赖版本；普通安装允许的依赖范围见 pyproject。

维护者可复制运行 `uv run python -m bench.package_smoke --output dist/package-smoke.json`：脚本自动在仓库外创建新环境，按锁定的运行时依赖安装当前 wheel，检查三语言原生、C 规则/模型修复、多错误修复、混合语言降级提示、自然语言生成、创意兜底、strict 失败、运行非零退出、凭据脱敏和原始许可文件。模型部分只使用本地假供应商；不代表真实模型质量。需要 uv、GCC、Node.js 及下载已锁定依赖的网络。

自用/受邀测试时，从 README 示例开始，再用自己的一份合法单文件程序和一份错误输入复核报告。反馈至少包含安装的版本/提交、OS/Python/GCC/Node 版本、最小可公开输入、完整命令、原生与 YesCC 的 stdout/stderr/退出码差异、报告状态；分享前移除源码与路径中的秘密。编译通过但行为错误需作为正确性失败报告，不能只附“成功”截图。

独立验收按路线图当前约定执行：用户已指定可由另一个全新 AI 会话进行黑盒测试，再由维护者审阅。AI 报告需如实标 AI，不称人工测试；开发助手自己的回归和准备检查不算独立验收。邀请动作、包上传及 Release 各自记录，当前任务状态以路线图 §10 为准。

可供测试者填写的最小反馈格式（维护者准备说明不等于已发出邀请）：


人工抽查另记录固定样本 ID、输入规格、预期输出依据、候选实际行为和结论；编译结果不能替代意图判断。维护者把经过确认的反馈证据存入 `docs/评测/`，任务勾选只更新路线图。


## 多错误输入与降级提示

`yescc run examples/multi_error.c --offline --no-fallback` 演示缺少 `#`、拼写、全角标点和分号的组合修复，预期 `value=7`。规则最多 24 次候选构建、每条路径最多 4 次细化；修改源码只保存在 `.yescc/`，复杂语义、错误变量/类型和跨语言输入仍可能失败。

确定性兜底的 `result.fallback.guidance` 与 stderr / explain 会说明是否为回显、offline 或模型配置/尝试限制及规则次数。JSON 构建模式仅输出报告。C++ 特征只作提示，不切换编译器或承诺转换；`cout <<` 写在 `.c` 中不等同于 C 语法错误。`--no-fallback` 适合只接受修复产物的试用，`--strict` 则连规则也关闭。补分号和编译成功仍不能证明复杂程序意图正确。


## 独立 AI 黑盒工作区

维护者已指定独立 AI 按普通用户功能说明测试，并授权开发主导者直接调用不继承开发历史的子 agent（`fork_turns=none`）完成后续测试；执行和证据复核不需要维护者逐次转交。准备器 `uv run python -m bench.prepare_blackbox --help` 仅准备目录，不启动测试 AI，也不产生验收结论；固定使用已归档 CI 验证的 RC2 wheel，拒绝覆盖现有工作区。

首轮 RC2 工作区 `~/ai-tests/yescc-rc2` 已完成并冻结，入口 `bin/yescc` 仍指向 RC2；不得用它验证新版本。已知缺陷的 RC3/RC4 定向复测分别保存在 `~/yescc-test-rc3`、`~/yescc-test-rc4`，被测命令以各自公开材料为准，原始报告不相互覆盖。新 AI 不应接收本项目聊天记录、源码、路线图或既有测试数据；仅按自身设计的用例测试，并将报告/证据留在 reports/、cases/、outputs/。配置模型时只允许本机假兼容端点与固定假密钥，未验证真实模型质量。

入口清除继承的环境和模型凭据，将 HOME/缓存/配置/tmp 指到独立目录；原生比较使用 `bin/test-env`。这是测试脚手架行为，不是产品新增能力；不能把脚手架拒绝地址等限制算作 YesCC 自身表现。它不提供强宿主文件系统/网络隔离，需测试 AI 遵守协议。后续子 agent 直接运行测试时同样使用白名单环境、外部超时和明确的测试目录写入边界；使用非登录 shell，避免加载宿主启动脚本。准备检查、独立 AI 测试、主导者复核与维护者最终审阅分别记录；定向复测不称新盲测或人工验收。


## JSON 命令错误与退出码

RC3 在有效位置使用 `--json` 时，对用法、输入等可预期错误返回结构化对象：`report_kind=command_error`，错误信息和退出码在 `error.message` / `error.exit_code`，捕获阶段为 `error.phase`。它不是完整构建报告，不猜测输入哈希、工具链、模型使用或费用；也不覆盖已有 report.json。其他正常报告继续沿用 schema v1。客户端应先识别对象种类，再读对应字段。

`--budget -1 --json` 可以得到解析错误 JSON；`run input.py -- --json` 中的 --json 属于用户程序，不触发此模式；选项参数值同理。help/version 仍显示文本，run --json 仍是用法错误，未捕获异常/信号/管道中断不能保证完整 JSON。

`--no-fallback` 只禁止创意兜底：缺失路径或参数用法错误为 100，不支持语言/编码为 101，支持语言的构建失败为 102，预算/尝试限制可为 103；不能把它当作强制返回 102 的开关。历史 RC2 黑盒工作区仍冻结，不用 RC3 覆盖旧报告或安装。

RC4 起，显式不支持的 `--lang`（含 `--play`）在模型会话和兜底之前返回101，保留旧报告；省略语言时的未知文本兜底及已支持别名仍可用。`--lang --json` 的 --json 是语言值，若没有另一个有效输出开关则返回文本错误。


## 独立二进制候选

构建入口 `uv sync --extra dev --extra release --locked`、`uv run python -m bench.binary_build --output dist/native`。只支持当前平台原生构建，不交叉编译；产物未发布，不替代 alpha 安装命令。Linux tar.gz/Windows zip 解压后保留整个目录，安装与三例见 README 的“免安装二进制”。

冻结CLI自带其Python运行时，但用户Python程序使用PATH中的真实Python3；报告工具链版本/产物由该解释器确定，用户依赖应安装在它的环境中。普通wheel不改变当前解释器。所有外部工具链调用撤销PyInstaller注入的库路径，避免GCC/Node/用户程序误加载内部共享库，不是增强安全沙箱。

`licenses/` 保存实际声明与审计；`MANIFEST.json` 保存逐文件校验与symlink；构建目录的 `binary-licenses.json` 会列 `unresolved`。文件存在不代表许可全覆盖，尤其注意静态编进CPython的库；未知项未解决不得正式发布。版本号0.1.0和Actions artifact均不代表正式tag/Release或PyPI安装已完成。
