# ADR-0019：可预期命令错误的 JSON 对象

- 状态：已实施（2026-11-09）；用户确认统一 JSON 错误输出，保留退出码含义。
- 补充 ADR-0005/0015；来自 RC2 独立 AI 黑盒报告 D1/D2。

## 决策

- 正常构建报告 schema v1 不改字段、类型或语义；历史落盘报告与 explain 的正常输出继续兼容。
- 有效位置的 `--json` 请求遇到 `FcompError` 可预期命令错误时，stdout 输出一个 JSON 对象，不再输出纯文本错误；退出码仍来自原错误类型。非 JSON 模式保留原 stderr 错误行为。
- 新错误对象用 `report_kind="command_error"` 区分正常构建报告，包含 `schema_version="1"`、tool、invocation.argv 与 error{type,exit_code,message,phase}。phase 为 parse / execute / explain，只说明捕获时阶段，不冒充更细的行为证据。
- 它不是构建报告，不填猜测的 input/toolchain/model/privacy/budget/result，也不写入或覆盖 `.yescc/<stem>/report.json`。解析失败可能没有可靠源文件；execute 阶段的异常也不应武断宣称零模型调用或费用。
- 客户端先判断 report_kind：command_error 读取 error.exit_code/message；否则按原构建报告处理。错误 code 与进程退出码一致；程序不应依赖报错文字或 Python 类名来分支。
- `--json` 位于选项值、工具链参数值或 `--` 后时不是该开关。即使解析器因前面的参数错误提前退出，也能识别后面有效位置的 JSON 请求。
- help/version 的既有纯文本动作不变；run 模式仍拒绝 `--json`，但该用法错误本身可以输出错误对象，不运行子程序；程序参数 `-- --json` 不影响输出模式。
- explain 没有报告时走同一个可预期错误路径。未捕获异常、进程被信号终止或管道故障不承诺总能形成完整 JSON；不把本次改动包装成对所有系统故障的保证。

## 退出码与 no-fallback

`--no-fallback` 禁止创意兜底，不统一重写错误分类：用法/路径 100、不支持输入/编码 101、构建失败 102、任务预算/尝试限制 103。未识别的文本输入带 strict/no-fallback 时仍返回 101，不因此进入自然语言/创意入口。修正 help 原来的“失败时返回102”文案，不改这些退出码。

## 验证与证据

原独立测试工作区与 RC2 安装保持冻结，原始报告、输入和输出单独归档，不覆盖独立证据。新候选为 RC3，新增命令级、参数位置、旧报告不覆盖和错误对象事实边界回归；失败审计输入 v2 不变，审计器另识别“无落盘报告但收到命令错误 JSON”，不假称 stdout 匹配落盘报告。

独立首轮只覆盖离线子集；模型与其他未测项继续标未测。修复回归属于开发者证据，不冒充独立 AI 复测或完整 G5 通过。


## RC3 定向复测后的实施补充（2026-11-11）

子 agent 观察到显式无效 `--lang` 默认会落入未知输入的兜底并覆盖原报告；strict/no-fallback 时则已按不支持语言返回 101。其最初的“非法语言必须 100”预期没有单独公开依据，不采用该错误码假设。

RC4 将已有显式语言识别放在模型会话与 `--play`/未知输入兜底之前：无效值统一使用原 `UnsupportedInput` 分类 101，有效别名继续由注册表识别，不改变省略 `--lang` 时的未知文本兜底。错误对象事实边界、JSON 开关位置和旧报告保护契约不变。测试者原报告与记录保持原样，主导者的缺陷判断及修复证据另行标注。
