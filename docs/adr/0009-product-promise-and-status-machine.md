# ADR-0009：产品承诺与结果状态机

- 状态：已接受（2026-11-04）；取代 [ADR-0002](0002-friendly-failure-semantics.md)
- 相关：[路线图 §1/§6.4](../项目路线图与发布计划.md)、[需求报告 §11.2](../初版需求报告.md)

## 背景

v0.3 把「不报错」定义为「有限修复 + 友好终止」，优先保证不伪造成功。用户评审后认为这压掉了项目最独特的娱乐承诺：无论输入什么，都尽量得到一个能运行的程序。两者并非不可兼容——关键是把「生成了程序」和「实现了意图」分成不同状态。

## 决策

产品承诺改为三条：

1. 正确代码绝不打扰（原生成功即结束，0 改写、0 模型调用）。
2. 错误代码尽力挽救（规则 → 便宜/本地模型 → 强模型，每层真实编译验证）。
3. 无意义输入也给出创造性解释（确定性兜底、文化梗、模型创意解释）。

结果状态机：

| 状态 | 含义 | 退出码 |
| --- | --- | --- |
| `native_ok` | 原生成功，源码未改 | 0 |
| `repaired` | 规则或模型修复后真实编译通过 | 0 |
| `generated` | 自然语言/伪代码生成后真实编译通过 | 0 |
| `creative_fallback` | 生成了可运行但非意图等价的程序 | 0（stderr 强提示） |
| `failed` | 未产出，且兜底也失败 | 102/103/104 |

兜底边界：

- 只对**输入类**失败生效（语法、语义、意图不明、非代码文本）。
- 环境类失败（缺工具链、缺依赖、权限、磁盘）不得兜底，必须如实报错。
- 源码兜底必须保留原始诊断、原始输入、兜底原因，并在报告与 stderr 标注「不是原程序的修复」。
- `--strict` 关闭 AI 与兜底，回到原生失败语义（102 + 原始诊断）。
- 兜底产出程序时退出码为 0；脚本/CI 应使用 `--strict` 或 `--json` 的状态字段区分。

## 后果

- 正面：保住「永不扫兴」的体验，同时保留可追溯性与诚实边界。
- 负面：默认退出码 0 可能让脚本误判；通过 `--strict`、`--json`、stderr 提示和文档缓解。
- 风险：用户可能不读提示，把段子程序当成修复结果。发布清单要求审计「兜底状态是否被误标为成功」。
