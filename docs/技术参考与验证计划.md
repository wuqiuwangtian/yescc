## 1. 研究与官方文档依据

### 1.1 利用真实诊断进行程序修复

**Yasunaga、Liang，2020，Graph-based, Self-Supervised Program Repair from Diagnostic Feedback（DrRepair，ICML 2020）**。

- 来源：[论文入口](https://arxiv.org/abs/2005.10636)。
- 研究内容：把源码与诊断中的相关符号联系起来，通过程序反馈图与自监督训练进行修复，研究场景包括编程作业与程序合成结果。
- 项目推论：应保留并利用工具链的真实报错，让模型基于证据修复；产品界面隐藏报错，不等于内部也丢弃诊断。
- 适用边界：论文针对特定数据与任务，不能证明通用模型能正确修复所有语言或恢复任意自然语言意图。编译通过也不自动等于意图正确。
- 值得验证：在同一模型与预算下，“源码 + 诊断”是否比只给源码修得更好？局部上下文能否节省 token 而不明显降低正确率？

### 1.2 用程序行为评价自然语言生成

**Chen 等，2021，Evaluating Large Language Models Trained on Code**。

- 来源：[论文入口](https://arxiv.org/abs/2107.03374)。
- 研究内容：使用 HumanEval 等方式评估由描述生成代码的功能正确性，并研究多次采样带来的改善。
- 项目推论：优先使用独立执行测试判断功能，而不是只看代码像不像答案；默认一次生成的质量与多次尝试后的成功率应分开统计。
- 适用边界：Python 短函数基准不能代表全部语言、真实项目或含糊的中文需求；有限测试通过也不等于形式化证明。旧论文的模型表现不作为当前模型选型依据。
- 值得验证：pass@1 与固定两轮修复的成功率分别是多少？每个正确结果实际花费多少，而不是只报“总有一次成功”的比例？

### 1.3 原工具链是语义兼容的依据

- [GCC 调用说明](https://gcc.gnu.org/onlinedocs/gcc/Invoking-GCC.html)：说明预处理、编译、汇编、链接及参数的作用。
- [GCC 错误与警告说明](https://gcc.gnu.org/onlinedocs/gcc/Warnings-and-Errors.html)：区分错误和警告，不支持把简单隐藏诊断当成修复。
- 项目推论：将原工具链调用、参数与环境保持作为独立能力；修复成功与合法程序兼容需要两套验收。
- 适用边界：GCC 文档不是 Python、JavaScript 或其他语言的语义规范；每个适配器应继续核查自己的官方规范及运行时文档。

### 1.4 编辑器插件可以复用命令行核心

- [VS Code Task Provider](https://code.visualstudio.com/api/extension-guides/task-provider)：任务扩展入口可用于构建与运行集成。
- [VS Code Language Server Extension Guide](https://code.visualstudio.com/api/language-extensions/language-server-extension-guide)：语言服务器适用于进一步提供诊断、补全与代码操作等语言能力。
- 项目推论：首个插件可以先做“包容地编译/运行”、报告和差异查看，再按需要加入语言服务，避免过早把全部核心逻辑绑进编辑器。
- 适用边界：LSP 不负责自动保证构建兼容或修复正确；也不能默认控制其他扩展产生的全部诊断。首版插件应说明自身处理范围。

## 2. 建议的对照实验

| 方案 | 处理方式 | 主要问题 |
| --- | --- | --- |
| A | 原工具链 | 合法程序的基准行为，以及错误样本的原始失败情况 |
| B | 原工具链 + 小范围规则 | 常见符号问题有多少不需要模型就能处理？ |
| C | 原工具链 + 规则 + 本地模型 | 在无云端调用时，能提升多少正确修复？ |
| D | 原工具链 + 规则 + 云端模型 | 云端增加的成本和等待是否换来足够收益？ |

每种方案固定最大轮数和相同上下文政策，记录规则与模型实际参与比例。若某任务没有尝试模型，也计入整体用户体验，不能只挑模型成功时报告。

合法程序应该在 B/C/D 中始终走原生成功路径；这一组重点是保持行为和开销，而不是模型能力。

## 3. 三类样本与标注方式

### 3.1 合法代码：验证不干扰

建议首轮每种候选语言至少准备 30 个短程序，覆盖函数、循环、文件读写、标准输入、Unicode、模块/链接和参数差异；这是发现问题的起始规模，不是兼容性认证。

测试时固定运行时、环境和输入，分别执行原工具链与包装工具。除结果外还核对源码未被改写、模型调用为零、路径与产物正确。对有意输出 stderr 或返回非零状态的程序，不能把结果擅自改成“正常”。

### 3.2 损坏代码：验证恢复意图

先从有独立测试的正确程序出发，生成不同损坏类型：缺括号/引号、全角标点、缩进、标识符笔误、类型不匹配、多处错误组合。中文字符串和注释本身应作为保留内容，不能把所有中文都视为错误。

损坏前代码提供行为参考，但不直接暴露给修复模型；修复结果不要求逐字恢复源码，只要求通过能覆盖原功能的独立测试。一次损坏若引入多种合理意图，要标记歧义而非强行判唯一答案。

再加入真实新手错误样本和跨文件问题，单独报告；合成标点错误上的高分不能外推到真实项目。

### 3.3 自然语言：验证语义

建议准备 30–50 个中文任务作为首轮探索，包含明确需求、边界输入和描述缺失三类。例如“读入整数输出最大值”应明确空输入和非法输入如何处理；“排个序”则应标记缺少顺序、数据类型和输入输出格式。

任务描述、预期行为、关键假设和隐藏测试应在生成前准备。覆盖算法、小型文本处理和受控文件操作；不以少量算法题声称可以生成任意应用。

模型编写的自测可以帮助找问题，但最终结果要与独立测试、规格和必要人工复核交叉验证，防止模型同时误解实现与测试。

## 4. 统一记录与决策指标

| 指标 | 定义或用途 |
| --- | --- |
| 原生兼容率 | 固定环境内，与原工具链行为一致的合法样本比例 |
| 构建成功率 | 能真实产生对应语言合法产物的比例 |
| 意图正确率 | 满足独立规格/测试并通过必要复核的比例 |
| pass@1 | 一次生成候选就符合功能要求的任务比例；与两轮修复后的比例分开 |
| 不必要修改率 | 原工具链接受的代码被改写，或修复触及无关功能的情况 |
| 假成功率 | 报告成功但无有效产物、未完成验证或行为不合要求的情况 |
| 性能 | 冷/热路径 P50/P95，含工具链耗时与包装开销分项 |
| 成本 | 任务 token、调用次数、金额、本地峰值内存与模型加载时间 |
| 单个正确结果的成本 | 总实验成本 / 正确任务数，包含失败任务消耗 |
| 失败收敛 | 超时、超预算、取消后是否及时停止且状态准确 |

“未完成验证”不能自动等于失败的程序，但必须在结果中独立标注，不能混入已验证成功。报告测试覆盖范围，不把测试通过写成“已证明绝对正确”。

## 5. 首先排查的产品冲突

1. **默认无报错与脚本集成**：建议界面不直接显示内部诊断，同时保留准确退出码与可读报告；失败时用友好状态结束，而不是始终返回 0。
2. **合法行为一致与自动修复**：建议原生成功即停止，不因警告或模型认为可以优化而改代码。
3. **所有语言与可验收范围**：完整愿景保留，但每个发布版本列清语言、实现、版本、平台和能力层次。首版分期需后续确认。
4. **自动理解与意图歧义**：不可能从任意输入唯一推断愿望；应记录假设，必要时允许一次轻量澄清。
5. **低延迟与迭代求解**：限制重试与上下文，用固定预算比较效果；不能把无上限重试伪装成快速编译。

## 6. 可行性阶段建议交付

下一阶段如果启动开发，建议先交付一份跨平台结果表：每个语言/工具链组合的原生一致性、常见错误意图正确率、自然语言 pass@1、预算内最终成功率、P95 延迟和单个正确结果成本。

有了结果再决定首批支持语言、本地与云端分工、是否值得扩展到项目级输入。当前阶段没有代码、性能数据或支持声明。
